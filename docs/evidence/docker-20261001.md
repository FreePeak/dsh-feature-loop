# Docker path — verified 2026-10-01

The evidence report of 2026-09-30 lists this path as **UNTESTED** (`OrbStack
down`). The daemon was up today, so it was run end to end. It was broken in four
ways, none of which produced an error.

Harness: `@deepseek-ai/dsh@0.2.0-rc.2` (was pinned to `0.1.7-alpha.1`).
Image: `dsh-feature-loop:local`, 1.64 GB.

## What was wrong, and what each symptom looked like

| # | Symptom | Cause | Fix |
|---|---|---|---|
| 1 | `npm install` in the plugin stage fails, exit 127 | `package.json`'s `prepare` script runs `git config`, and `node:22-slim` has no git | `prepare` becomes `git config … \|\| true` |
| 2 | Boot logs `feature-loop: failed to import`, **and nothing else** | The runtime stage copied `lib/` but not `assets/`; `src/dashboard.ts`'s `readBundleAsset()` throws on the missing vendored bundle | copy `assets/` and `client.js` from plugin-build, and import the bundle **at build time** from inside the profile |
| 3 | Boot is clean, no `feature-loop dashboard:` line, and the published dashboard port connects to nothing | `docker/profile.patch.yml` had `dashboard.enabled: true` and **no `standalone: true`** | add it |
| 4 | Every model call in the container dies with `llm-deepseek: no API key for provider route "deepseek-official"` | No `agent-default-model` row: the loop ran on the harness's own default instead of the gateway | add the row to the profile patch |
| 5 | `make dashboard` prints a URL on a port nothing is published to | `make up` passed `DSH_HOST_PORT` but not `DSH_DASHBOARD_PORT`, so compose used its default while the target printed the variable | pass both |

A fresh container also has **no Workspace** — `/data/storages/workspace.json`
carries `"workspaceIds": []` — so the Feature Loop page correctly refuses to
start a loop until one is added. Not a bug, but the first thing that makes a
fresh container look broken; now documented in `docker/README.md`.

## Evidence, in the order the checks ran

### The image builds

```
#21 4.405 feature-loop imports      ← the new build-time import check
 Image dsh-feature-loop:local Built
```

That one line is the check worth having. `--dump-config` shows the
`feature-loop` row whether or not the module imports — `client-modules` reads
`dsh.client` from `package.json` on disk and never imports it — and the loader
prints `failed to import` as a **warning** the boot carries straight past. So the
old build produced a container that booted clean, served a UI, and gated
nothing. The import now runs from inside the profile (where the peers resolve),
so this class of failure is a build error:

```
#21 6.144 Error [ERR_MODULE_NOT_FOUND]: Cannot find package '@deepseek-ai/schemastery'
        imported from /opt/feature-loop/lib/index.mjs
```

— which is what the first attempt at that check produced, importing from the
install directory instead. That error is about the *check*, not the plugin, and
it is the reason the check lives where it does.

### It boots, with both surfaces

```
feature-loop dashboard: http://127.0.0.1:8100/?token=<redacted>
dsh web: http://127.0.0.1:3099/?token=<redacted>
```

Two token lines, and the first only appears with `standalone: true`.

### Both surfaces answer, on the published host ports

| Probe | Result |
|---|---|
| `GET :3192/?token=…` (dashboard page) | **200**, 4216 bytes |
| `GET :3192/api/state?token=…` | `{"answers":true,"pending":[],"runs":[],"feed":[…],"watching":true}` |
| `GET :3192/assets/dashboard.js` | **200** |
| `GET :3190/?token=…` → follow redirect | **200**, and the client bundle graph carries `@freepeak/dsh-feature-loop/client.js` |
| `POST :3192/api/approvals/<id>?token=…` | **409** `no such pending approval` |

That last row is PR #28's fix working in a container: the settle route used to
require the `x-dashboard-token` header, so a `?token=` POST was a 401 that read
as "wrong token". It now reaches the route and gets the honest answer — the id
does not exist — from a plain `curl` with no header at all.

## What is still unverified

**A gated step, clicked, in the container.** The dashboard serves, the plugin
imports, and the config is right, but no HITL cycle was driven inside the
container — the browser pass got as far as the Feature Loop page rendering with
its own note ("No workspace is registered yet"), which is the correct refusal and
not a run. Doing it needs a workspace registered in the container and a gateway
route reachable from inside it, which is a longer setup than this pass covered.

The same cycle **is** proven twice outside the container, on the same build and
the same policy row: `make e2e-in-ui` against a local profile
([`../VERIFY-E2E-APPROVAL.md`](../VERIFY-E2E-APPROVAL.md)) and the standalone
dashboard (`make e2e-dashboard`). The container differs in three ways that touch
this path — the `0.0.0.0` dashboard bind, the published-port relay, and the
profile being baked rather than hand-built — and none of the three is on the
gate's decision path.

Recorded rather than claimed, because the honest status is "the container
serves a working plugin and no one has clicked Approve in it yet".
