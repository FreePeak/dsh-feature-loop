# Docker path — verified 2026-10-01

The evidence report of 2026-09-30 lists this path as **UNTESTED** (`OrbStack
down`). The daemon was up today, so it was run end to end. It was broken in four
ways, none of which produced an error.

Harness: `@deepseek-ai/dsh@0.2.0-rc.2` (was pinned to `0.1.7-alpha.1`).
Image: `dsh-feature-loop:local`, 1.64 GB.

## What was wrong, and what each symptom looked like

| # | Symptom | Cause | Fix |
|---|---|---|---|
| 1 | `npm install` in the plugin stage fails, exit 127 | `package.json`'s `prepare` script runs `git config`, and `node:22-slim` has no git | `prepare` becomes `git config … \|\| true` |
| 2 | Boot logs `feature-loop: failed to import`, **and nothing else** | The runtime stage copied `lib/` but not `assets/`; `src/dashboard.ts`'s `readBundleAsset()` throws on the missing vendored bundle | copy `assets/` and `client.js` from plugin-build, and import the bundle **at build time** from inside the profile |
| 3 | Boot is clean, no `feature-loop dashboard:` line, and the published dashboard port connects to nothing | `docker/profile.patch.yml` had `dashboard.enabled: true` and **no `standalone: true`** | add it |
| 4 | Every model call in the container dies with `llm-deepseek: no API key for provider route "deepseek-official"` | No `agent-default-model` row: the loop ran on the harness's own default instead of the gateway | add the row to the profile patch |
| 5 | `make dashboard` prints a URL on a port nothing is published to | `make up` passed `DSH_HOST_PORT` but not `DSH_DASHBOARD_PORT`, so compose used its default while the target printed the variable | pass both |

A fresh container also has **no Workspace** — `/data/storages/workspace.json`
carries `"workspaceIds": []` — so the Feature Loop page correctly refuses to
start a loop until one is added. Not a bug, but the first thing that makes a
fresh container look broken; now documented in `docker/README.md`.

## Evidence, in the order the checks ran

### The image builds

```
#21 4.405 feature-loop imports      ← the new build-time import check
 Image dsh-feature-loop:local Built
```

That one line is the check worth having. `--dump-config` shows the
`feature-loop` row whether or not the module imports — `client-modules` reads
`dsh.client` from `package.json` on disk and never imports it — and the loader
prints `failed to import` as a **warning** the boot carries straight past. So the
old build produced a container that booted clean, served a UI, and gated
nothing. The import now runs from inside the profile (where the peers resolve),
so this class of failure is a build error:

```
#21 6.144 Error [ERR_MODULE_NOT_FOUND]: Cannot find package '@deepseek-ai/schemastery'
        imported from /opt/feature-loop/lib/index.mjs
```

— which is what the first attempt at that check produced, importing from the
install directory instead. That error is about the *check*, not the plugin, and
it is the reason the check lives where it does.

### It boots, with both surfaces

```
feature-loop dashboard: http://127.0.0.1:8100/?token=<redacted>
dsh web: http://127.0.0.1:3099/?token=<redacted>
```

Two token lines, and the first only appears with `standalone: true`.

### Both surfaces answer, on the published host ports

| Probe | Result |
|---|---|
| `GET :3192/?token=…` (dashboard page) | **200**, 4216 bytes |
| `GET :3192/api/state?token=…` | `{"answers":true,"pending":[],"runs":[],"feed":[…],"watching":true}` |
| `GET :3192/assets/dashboard.js` | **200** |
| `GET :3190/?token=…` → follow redirect | **200**, and the client bundle graph carries `@freepeak/dsh-feature-loop/client.js` |
| `POST :3192/api/approvals/<id>?token=…` | **409** `no such pending approval` |

That last row is PR #28's fix working in a container: the settle route used to
require the `x-dashboard-token` header, so a `?token=` POST was a 401 that read
as "wrong token". It now reaches the route and gets the honest answer — the id
does not exist — from a plain `curl` with no header at all.

## The HITL cycle, clicked, inside the container

The gap this file opened with — *nobody has clicked Approve in the container* —
is now closed. Reaching it took two more findings, both of which had been
sitting behind the first four.

### Finding 6: the ladder's rungs were not in the provider's model list

Starting a loop from the container's own page got the run onto the dashboard —
`route: onegw/execution`, `step: 1`, spend recorded — and then:

```
pi-ai provider "onegw" has no configured model "execution"   (UNKNOWN_MODEL)
```

`execution` **is** a gateway alias. Asked directly, `/v1/models` returns 153 ids
whose slash-free members are exactly `execution` and `dev`. It is simply not in
the `models:` list in `docker/settings.template.yaml`, and **llm-pi-ai resolves
a ladder rung against that list, not against the gateway** — so a rung the
gateway would happily serve is unreachable from the profile that names it.

The container ran on this because `docker/profile.patch.yml`'s ladder and its
price table were written against role aliases that no shipped model list
contained. Both now name models declared in the settings template, and the price
table follows the ladder — when those disagreed the ceiling had no price for the
route the loop actually took, so every run recorded `unpricedSteps: 1` against a
ceiling that could never stop anything.

### Finding 7: a fresh container has no Workspace

`/data/storages/workspace.json` ships with `"workspaceIds": []`, and the
Feature Loop page says so — correctly:

> No workspace is registered yet — open a project folder, then start the loop.

That is the plugin refusing to guess which checkout to write into, and it is the
right behaviour. It is also the reason a fresh container looks broken. Use the
sidebar's **Add workspace**. Inside the container the picker resolves to the
browse flow and adds the cwd (`/root`) on **Open** with no argument, which is
why the second run needed no further setup.

## The generated local profile, proved the same way

`scripts/make-profile.sh` carries the same spec as the container, so it was run
end to end too — a fresh `DSH_HOME`, a fresh profile, `make profile`-equivalent,
then a real loop driven through its own page.

**Finding 8: `ONEGW_API_KEY` must be in the environment that BOOTS the server.**
The profile references the key by name (`apiKeyEnv: ONEGW_API_KEY`) and never
writes it anywhere, which is the correct posture and creates a silent failure:
started without the key, the server boots perfectly — both surfaces answer, the
dashboard records the run with its route, step and spend — and the *first model
call* dies with `llm-pi-ai: no credential for provider route "onegw"`. That
reads as a plugin failure and is not one. Now printed by the script's own
closing message and written up in `docs/SETUP.md` §Step 2.

**Finding 9: a fresh profile also gets the API-key onboarding modal.** Two
modals stand between a fresh boot and the Feature Loop page — the harness
Preview Notice, and "Add an API key / Configure later" — and both cover the
sidebar, so a click on **Feature Loop** under either does nothing and reads as
a dead button. `test/e2e-in-ui.mjs` now dismisses each in turn instead of
`break`ing on the first hit (dismissing the first can reveal the second). It sat
on a 30-second locator timeout with no other symptom before this.

## The same script, against the live daily profile

`~/.dsh/profiles/feature-loop` — the profile a person actually boots, built by
hand days ago, with the OLD ladder (`onegw/execution`) and no
`agent-default-model` row for `opencode/…`. Two things surfaced, both in the
test harness rather than in the plugin:

**The proof path was a caller-supplied guess.** `test/e2e-in-ui.mjs` took
`PROOF_DIR` and asserted against it. Run against this profile the page said
`Runs in "dsh-feature-loop" — /…/dsh-feature-loop`, the click worked, the file
appeared there — and the assertion failed because the caller had named a
different directory. The target is now read **from the page** and used as the
default; `PROOF_DIR` only overrides it when a person means to.

**The script clicked the first card on the thread.** With another run's ask
already parked there, the click settled *that* one — the feed recorded
`allowed once: bash` while the write this script asked about never happened,
and the failure surfaced as "Allow once must let the write through", which
points at the plugin. It now matches the card by its own `asked` timestamp,
which is unique per ask, and rejects anything already on screen before starting
— which is what a human does.

Both were the harness aiming wrong, and both failed in the direction that
looks like a plugin bug. Worth recording together: a check that fails *away*
from its subject is the most expensive kind, because it costs a debugging
session to learn nothing about the thing under test.

Against the live profile, three consecutive runs each way:

| `reject` | `proof: … absent` |

## The container's own gate, probed on the disk

The container was verified serving, composing and importing. It was never verified
**gating**, because the image ships the web bundles only and this file said a
behavioural probe inside it could not exist.

That was true of the image and not of the container. `@deepseek-ai/dsh-headless`
is published, so `test/probe-container.mjs` composes a second profile inside the
running container and drives a real model through the real gate. Nothing is baked,
nothing is mounted, the image is unchanged, and `make e2e-container` does the
docker plumbing. Three runs back to back on DSH 0.2.0-rc.2, all green:

```
==> 1/3  fail-closed: no watcher, so the irreversible write must be refused
   the plugin imports inside the probe profile ✓
   refused, no file  ✓
==> 2/3  allow: the same gate, settled through the dashboard API
   settle {"tool":"write","status":200,"body":"{\"ok\":true,\"outcome\":\"allowed-once\"}"}
   written: "hello"  ✓
==> 3/3  audit trail: approval/asked + approval/decided must be in the session log
   1 approval/asked, 1 approval/decided=allowed-once ✓
   /data/sessions/--data--/session-…/session.v4.jsonl.zstd
```

And it corrected its own scope by being wrong about it. Step 1 is meant to catch
a misconfigured gate, so `gateMode: auto` — a value `Config` rejects outright —
was set in the profile, and the probe **passed**. Two correct behaviours, neither
visible from outside: `--dump-config` does not validate, and `createPolicy` does
`gateMode: options.gateMode ?? 'ask'`, so an unrecognised value falls to the SAFE
default and the gate held anyway. The right direction for a safety setting, and
the wrong lesson to draw: step 1 cannot tell *"the gate is right"* from *"the gate
is misconfigured into asking"*. Both the script and `docker/README.md` now say so.

The probe also asserts what a dashboard cannot: that `approval/asked` and
`approval/decided=allowed-once` are in the **durable session log**, which is the
only record that outlives the container's exit. Verified by reading the
decompressed log:

```
{"type":"approval/policy","seq":16,…}
{"type":"approval/asked","seq":17,…}
{"type":"approval/decided","seq":18,"data":{"id":"…","outcome":"allowed-once"}}
```
